# Chat applications

Write a message that lets people understand the point and act without reconstructing the conversation. Preserve names, mentions, links, and quoted text. Do not invent an owner, commitment, deadline, consensus, action, or sender identity.

- **Thread reply:** Answer the point raised in the existing thread. Build the reply from completed work, actions taken, decisions, evidence, results, material limitations, and the next checkpoint. An unused option with no effect is not message content. Include a rejected approach only when it directly affects the outcome.
- **Status update:** State the current condition and impact, then the known owner or next checkpoint. Name a time only when the source provides one.
- **Request:** Put the requested action first, followed by the minimum context and any supplied deadline.
- **Announcement:** State what changed, who it affects, and what they need to do.
- **Decision:** State the decision, the reason that changes how people act, and any known follow-up.

Use short prose for one point and bullets only for parallel facts or actions. If a message needs a clear action, name its actor. If the next update depends on a condition, state the condition without promising who will post it unless the source identifies that person.

Reply in the same thread when answering a message, following up on your own message, confirming a finding, or reporting that a change landed. Start a new thread only when starting a new, unrelated conversation. Keep one point in one thread.

Material skipped checks and limitations still belong in the message when the reader needs them. Drafting a message does not authorize sending it. When a connected chat system is in scope and sending is authorized, resolve a settled thread where the application supports it.
