# Issue trackers

Shape the requested artifact so another person can assess, prioritize, implement, or verify the work. Preserve the established field structure. Omit unknown metadata rather than guessing an owner, priority, estimate, date, severity, or workflow state.

- **Title:** State the problem or requested outcome in specific, searchable terms.
- **Bug description:** Give the current behavior, impact, evidence or reproduction, and expected behavior. Distinguish observation from inference.
- **Work item description:** Give the context, intended outcome, constraints, and acceptance criteria supplied or directly implied by the request.
- **Acceptance criteria:** Use observable completion conditions. Do not expand the requested scope with speculative edge cases.
- **Comment or reply:** Build the update from completed work, actions taken, new decisions, evidence, blockers, and results. Add only the context needed to act. Omit unperformed work and approaches that were considered but not used. Include a rejected approach only when it directly affects the outcome or explains a constraint the reader could otherwise hit.
- **Status update:** State what changed, what evidence supports it, and what remains.

Reply in the same thread when answering a comment, following up on your own comment, confirming a finding, or reporting that a change landed. Start a new thread only when starting a new, unrelated conversation. Keep one point in one thread. Resolve it once settled where resolving is supported and authorized.

Material skipped checks and limitations still belong in the comment when the reader needs them. Drafting content does not authorize creating, editing, assigning, transitioning, or closing an issue.
